h1. Proteção de Múltiplos Recursos em Delphi

*Versão:* 1.0
*Referência:* [Try-Finally Blocks for Protecting Multiple Resources in Delphi|https://blogs.embarcadero.com/try-finally-blocks-for-protecting-multiple-resources-in-delphi/] - Marco Cantù, Embarcadero

----

h2. 1. Objetivo do documento

Este documento descreve as práticas corretas e incorretas para proteção de múltiplos recursos (objetos) em Delphi, quando há risco de exceções durante criação ou destruição.

{info}
O projeto *ProtectingTwoObjects* demonstra na prática cada cenário. Execute os botões 6, 7 e 8 para ver a diferença crítica entre try aninhado e os padrões flat.
{info}

----

h2. 2. Contexto e problema

h3. 2.1 O cenário

Em Delphi, ao alocar dois ou mais objetos que precisam ser liberados ({{Free}}), surge a questão: *como garantir que todos sejam liberados mesmo quando ocorre uma exceção?*

Recursos podem falhar em dois momentos:
* *Durante a criação* ({{Create}}): se o segundo objeto falhar ao ser criado, o primeiro já foi alocado e pode ficar sem liberação.
* *Durante a destruição* ({{Destroy}}): se o primeiro {{Free}} levantar exceção, o segundo {{Free}} no mesmo bloco {{finally}} pode nunca executar.

h3. 2.2 Consequências

||Consequência||Impacto||
|Memory leak|Objetos não liberados consomem memória|
|Acesso inválido|Chamar {{Free}} em referência não inicializada pode gerar Access Violation|
|Comportamento indefinido|Variáveis locais não inicializadas possuem valor indefinido|

----

h2. 3. Casos incorretos (como NÃO fazer)

h3. 3.1 Caso 1: Memory leak quando A2.Create falha

Ambos os objetos são criados *antes* do bloco {{try}}. Se a criação de A2 falhar, A1 nunca é liberado.

{code:pascal|title=Errado}
LA1 := TTest.Create('A1');
LA2 := TTest.Create('A2');  // Se falhar aqui, LA1 nunca é Free!
try
  LA1.DoSomething;
  LA2.DoSomethingWith(LA1);
finally
  LA2.Free;
  LA1.Free;
end;
{code}

*Demo:* Botão 1 - Exceção + mensagem [LEAK] A1 nunca foi destruido

h3. 3.2 Caso 2: Free em variável não inicializada

A2 é criado *dentro* do try. Se {{Create}} falhar, LA2 fica com valor indefinido. O {{finally}} tenta {{LA2.Free}} - Access Violation ou comportamento indefinido.

{code:pascal|title=Errado}
LA1 := TTest.Create('A1');
try
  LA2 := TTest.Create('A2');  // Se falhar, LA2 indefinido
  ...
finally
  LA2.Free;  // PERIGO
  LA1.Free;
end;
{code}

----

h2. 4. Soluções corretas (sem falha nos objetos)

h3. 4.1 Solução 1: Try-Finally Aninhados

Cada recurso possui seu próprio bloco try-finally.

{code:pascal|title=Correto}
LA1 := TTest.Create('A1');
try
  LA2 := TTest.Create('A2');
  try
    LA1.DoSomething;
    LA2.DoSomethingWith(LA1);
  finally
    LA2.Free;
  end;
finally
  LA1.Free;
end;
{code}

*Vantagens:* Muito claro, cada recurso protegido individualmente
*Desvantagens:* Mais verboso, aninhamento com muitos recursos

h3. 4.2 Solução 2: A2 := nil

Inicializar A2 com nil protege contra {{Free}} em variável indefinida ({{Free}} em nil não faz nada em Delphi).

h3. 4.3 Solução 3: A1 := nil; A2 := nil

Padrão balanceado e uniforme para 3, 4 ou mais recursos.

{warning}
*IMPORTANTE:* As soluções 2 e 3 funcionam apenas quando *não há exceção no Destroy*. Se o {{Destroy}} do primeiro objeto falhar, o segundo nunca é liberado (veja seção 5).
{warning}

----

h2. 5. Falha no Destroy: O teste decisivo

Quando o *Destroy* do primeiro objeto (A2) levanta exceção:

||Solução||Protegido?||Motivo||
|Try Aninhado|✓|Finally externo ancora executa LA1.Free|
|A2 := nil|✗ LEAK|LA2.Free e LA1.Free no mesmo finally - LA1.Free nunca executa|
|Ambos nil|✗ LEAK|Mesmo problema|

*Demo:* Botões 6, 7 e 8 demonstram essa diferença. Apenas o 6 mostra "[OK] A1.Destroy executado" no log.

----

h2. 6. Solução com Interface (Reference Counting)

Uso de interfaces com {{TInterfacedObject}} - *sem try-finally necessário*.

h3. 6.1 Funcionamento

* Variáveis do tipo interface incrementam/decrementam ref count automaticamente
* Ao sair do escopo (normal ou por exceção), objetos são liberados
* Método {{New}} retorna a interface - factory pattern

h3. 6.2 Exemplo

{code:pascal|title=Com Interface}
procedure Exemplo;
var
  LA1, LA2: ITest;
begin
  LA1 := TTestInterface.New('A1');
  LA2 := TTestInterface.New('A2');
  LA1.DoSomething;
  LA2.DoSomethingWith(LA1);
  // Sem try-finally! Ao sair, ambos liberados automaticamente.
end;
{code}

*Demo:* Botões 9 e 10 - nenhum leak, mesmo com exceção no botão 10.

h2. 8. Conclusões e Recomendações

{info}
*Resumo:* Apenas *try-finally aninhado* ou *interface* garantem liberação em todos os cenários. Os padrões flat (A2 nil / ambos nil) falham quando {{Destroy}} levanta exceção.
{info}

*Recomendações:*
# *Novo código:* Preferir interfaces quando possível
# *Código legado:* Usar try-finally aninhado para múltiplos recursos
# *Evitar:* Padrão flat quando Destroy pode falhar
# *Validação:* Usar {{ReportMemoryLeaksOnShutdown := True}} em desenvolvimento
